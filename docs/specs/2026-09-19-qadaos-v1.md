# QadaOS v1: Prayer Debt Ledger with Switchable Strategies

**Date:** 2026-09-19
**Status:** Spec complete, ready for implementation
**Systems touched:** all greenfield. Ledger domain engine, prayer-time engine, strategy engine, local-first client store and sync, Next.js API, Postgres schema, auth, Web Push reminders, PWA shell, onboarding, home / log / plan / stats UI, export and account deletion.

## Summary

QadaOS is an installable web app (PWA) that tracks a Muslim's missed-prayer debt and their daily prayers going forward in one ledger, then lets them run switchable catch-up strategies on top of it without ever corrupting the numbers. Every fact is an immutable event; debt, targets, adherence and projections are derived. It is a public, multi-tenant, open-source service hosted on Vercel, signed in with Google plus passkeys, fully usable offline, with push reminders at prayer times.

The first user owes about 20,000 prayers (about 4,000 missed days). The product must make a bad day (missed daily prayers, no qada) as easy and shame-free to record as a good one.

## Decisions

Every interview decision, one line each: the choice, the rejected alternative(s), why.

1. **Append-only event ledger, derived state.** Rejected: mutable per-prayer counters. Counters make strategy switches, undo, backdating and estimate corrections lossy. Events make them free and make sync a set union.
2. **Sync backend from day one.** Rejected: local-only with export, or local-first now and sync later. The user wants multi-device durability and server-scheduled reminders in v1.
3. **Public multi-tenant hosted service.** Rejected: self-host with gated signup; single-user deployment. Anyone can sign up at the hosted URL, and anyone can also fork and self-host. This pulls abuse limits, account deletion, data export and a privacy policy into v1 scope.
4. **Google sign-in is the only login method, with passkeys as an upgrade after first login.** Rejected: magic link, email + password, Apple OAuth. No email provider is needed in v1.
5. **Local-first client with outbox sync.** Rejected: online-only with optimistic UI; offline-read-only. Logging Fajr with no signal must work. The client holds the full event log in IndexedDB.
6. **Next.js App Router on Vercel, Postgres (Neon via Marketplace), Drizzle, Serwist, Tailwind, adhan-js, web-push.** Rejected: Vite SPA + Hono on Cloudflare; SvelteKit + Turso. One repo, one deploy, forkable with one click.
7. **Daily misses are pending until the user resolves them.** Rejected: auto-mark missed at window close; no window logic at all. Debt is shown as confirmed plus pending. Nothing inflates silently.
8. **Strategies are composable rule sets with period history.** Rejected: single preset from a list; no plan engine. Each strategy change closes a period and opens a new one, and each period reports planned versus actual.
9. **Unmet daily targets reset each day; adherence records the gap.** Rejected: shortfall rolls into tomorrow; ask each morning. No second debt layer in the UI.
10. **Progress and pace, no streaks.** Rejected: gentle consistency signal; full streaks and milestones. No chains, flames or loss-aversion nudges anywhere.
11. **English only, no i18n plumbing.** Rejected: i18n-ready English; English plus Arabic with RTL. User's explicit call. Retrofitting later is accepted cost.
12. **Fiqh is configuration with neutral defaults.** Five prayers by default, Witr as an optional sixth column, Asr calculation selectable, prayer-time method selectable, no make-up order enforced. The first user's own profile uses the neutral defaults.
13. **Push reminders in v1: per-prayer reminders plus a daily review nudge, each toggleable.** Rejected: review nudge only; none.
14. **Home screen is direction A, "The Ledger", in neo-brutalist visual language with sparse playful stickers.** Rejected: B "One Button", C "Tiles". Language locked: cream ground, 2.5px black borders, 4px hard offset shadows, flat coral / violet / teal / yellow / sky fills, Archivo in heavy weights, pill tab bar.

## Assumptions (veto list)

Defaults chosen without explicit confirmation. Unvetoed = binding.

1. **Auth library is better-auth** with the Google provider, passkey plugin and Drizzle adapter. Auth.js would also work; better-auth has first-party passkeys.
2. **Reminder scheduler is a 5-minute schedule from Upstash QStash (Vercel Marketplace) hitting an idempotent dispatch endpoint.** Vercel Hobby crons run once a day, which cannot hit prayer times. If the deployment is on Vercel Pro, a Vercel cron every 5 minutes may replace QStash with no code change. The endpoint is schedule-agnostic and protected by a shared secret.
3. **Prayer day starts at Fajr.** A daily record is keyed by the Fajr-anchored local date, not the civil date. Isha's window ends at the next Fajr by default, with an "Islamic midnight" option in settings.
4. **Prayer windows:** Fajr [fajr, sunrise), Dhuhr [dhuhr, asr), Asr [asr, maghrib), Maghrib [maghrib, isha), Isha [isha, next fajr or midnight). A daily prayer becomes pending when its window closes without a resolution.
5. **Resolution statuses for a daily prayer:** `on_time`, `late`, `missed`, `exempt`. `late` means prayed after the window on the same prayer day. Only `missed` adds to debt. `exempt` covers menstruation, postnatal bleeding or any day with no obligation.
6. **Default calculation method is Muslim World League, default Asr is standard (Shafi'i), default high-latitude rule is "middle of the night".** All three are changeable in settings.
7. **Location is optional.** Denied or skipped location enters "no windows" mode: five plain daily checkboxes, no pending logic, no per-prayer reminders. Manual city search and GPS are both offered.
8. **Initial debt is entered per prayer, with an optional estimate wizard** (obligation start date, consistent-since date, optional exempt days per month, optional excluded ranges) that prefills the numbers. The numbers stay editable. Corrections later are `debt.adjust` events, never edits of the initial event.
9. **Debt may go below zero.** Past zero the UI shows "0 owed, N buffer". No celebration fires at exactly zero; a quiet "you have cleared your estimate" card appears with the buffer explanation.
10. **Qada logging is +1 / +N per prayer type, plus "log a full missed day" (one of each tracked prayer), plus a backdate control** that sets `occurred_at` and, for qada, the prayer day the log belongs to.
11. **Undo is a `event.revoked` event** targeting the original id. Any non-revoked event can be revoked from the Log tab. Revoking a resolution reopens the pending state.
12. **Progress is shown two ways:** count of prayers and count of rak'ah (Fajr 2, Dhuhr 4, Asr 4, Maghrib 3, Isha 4, Witr 3). Rak'ah view is the second toggle on the Stats tab.
13. **Projections:** "plan pace" simulates the active strategy's daily targets against current debt in type order until every column reaches zero. "Your pace" uses net progress (qada logged minus daily misses) over the trailing 30 days. If net pace is zero or negative, the projection says "not finishing at this pace" rather than a date.
14. **Adherence for a period** is the mean over its days of `min(done, target) / target`, ignoring days with zero target.
15. **Hijri date** is shown next to the Gregorian date using `Intl.DateTimeFormat` with the `islamic-umalqura` calendar, with a +1 / -1 day user offset in settings. No Hijri library.
16. **Sync protocol:** client pushes batches of events, server inserts with `ON CONFLICT (id) DO NOTHING` and assigns a monotonically increasing `server_seq`. Client pulls events with `server_seq` greater than its last seen. Settings are a single document with last-write-wins by `updated_at`.
17. **Abuse limits:** per-user sync push limited to 1,000 events per request and 60 requests per minute; auth and push-subscription routes rate-limited via the Vercel Firewall. Payload schemas validated with zod at every route.
18. **Account deletion is immediate and total** (all events, settings, subscriptions, sessions). **Export** is a JSON file of all events plus settings, and a CSV of daily debt totals. Both live in Settings.
19. **Privacy posture:** a short plain-language privacy page states that prayer data is stored to provide the service, is never sold or shared, and can be deleted at any time. Religious data is a special category; the hosted instance collects only what the ledger needs (Google id, email, display name, location as lat/lng and timezone).
20. **License is MIT.** README explains self-hosting: fork, create Neon and QStash via Marketplace, add Google OAuth credentials and VAPID keys, deploy.
21. **Strategy templates offered at onboarding:** "One with each" (1 same-type qada after each daily prayer), "Fajr first" (2 with Fajr, 3 at night, type order F D A M I), "Full day" (one complete missed day nightly), "Daily quota" (N of next-in-order). All editable after selection.
22. **Prayer times computed with adhan-js on both client and server** from the same stored parameters so reminders and UI agree.
23. **Reminder defaults:** per-prayer reminder at the start of each window, daily review nudge 45 minutes after Isha begins. Both off until the user enables them in onboarding or settings.
24. **iOS install guidance** is a dismissible card on first mobile visit explaining Share, then Add to Home Screen, because Web Push on iOS requires installation.
25. **Node 20 locally, Vercel default Node 24 in production.** Next.js 16, React 19, Tailwind 4, TypeScript strict.

## Deferred Unknowns

Open question → conservative default → evidence to depart.

1. **Matching logged qada to strategy targets within a day** → greedy: per prayer type, fill rules in declaration order → depart if users report confusing target progress with mixed rules.
2. **Timezone travel across a prayer day** → the prayer day is computed from the timezone stored at the time of each event; the current day uses the device timezone → depart if travelers report duplicated or missing days.
3. **Server-side derived state cache** → none; the client reduces events locally and the server reduces on demand for reminders → depart to a per-user snapshot table if a user exceeds roughly 50,000 events or reminder dispatch exceeds its time budget.
4. **Push subscription per device versus per user** → per device, keyed by endpoint, pruned on 404 / 410 → no change expected.
5. **Concurrent resolutions of the same day and prayer from two devices** → latest by `(occurred_at, id)` wins → depart only if it visibly misbehaves.
6. **Service worker update prompt** → Serwist default with a "New version, tap to reload" toast → no change expected.
7. **Vercel plan tier** → assume Hobby, use QStash → switch to Vercel cron if Pro is confirmed.

## Requirements

1. A user can sign up and in with Google, then register a passkey and sign in with it.
2. A user completes onboarding: location (or skip), prayer-time method and Asr rule, tracked prayer set (five, optionally Witr), initial debt per prayer (manual or wizard), a starting strategy from templates, reminder opt-in.
3. The home screen shows total owed, owed per prayer as progress bars, today's prayers with state (done, pending, now, upcoming, missed, exempt), the active strategy's targets with progress, and one primary action for the current window.
4. A user can mark the current daily prayer as prayed in one tap.
5. A daily prayer whose window closed without a resolution shows as pending and can be resolved as on time, late, missed or exempt. Pending never converts to debt automatically.
6. A user can log qada by +1 / +N per prayer, log a full missed day, and backdate any log.
7. A user can undo any event. Undo is itself recorded.
8. A user can adjust the initial estimate later with a note; the adjustment is visible in the log.
9. A user can create, edit, switch and stop strategies composed of rules (with-daily, timed block, daily quota) plus a type order. Switching closes the current period and opens a new one.
10. The Plan tab shows today's targets, the strategy's projected finish, and a history of periods with adherence.
11. The Stats tab shows debt over time, net progress per day for the last 7 and 30 days, count and rak'ah views, and projections at plan pace and actual pace.
12. Everything above works offline. Events queue and sync when online. An offline banner shows the count of unsynced changes.
13. Two devices signed into one account converge to the same ledger.
14. A user can enable per-prayer reminders and a daily review nudge, each toggleable, delivered by Web Push at that user's prayer times.
15. A user can export all data and delete their account from Settings.
16. The app installs to the home screen on iOS and Android with a proper manifest, icons, splash and standalone display.
17. Anyone can self-host from the repository with documented environment variables.

## Technical Design

### Domain package (`src/domain`, pure TypeScript, zero React or DB imports)

Single source of truth for math. Runs identically in the browser, in tests and on the server.

**Prayer types:** `fajr | dhuhr | asr | maghrib | isha | witr`. Rak'ah weights as in Assumption 12.

**Events** (`LedgerEvent`): `{ id: uuid, type, occurredAt: ISO string, tz: IANA string, deviceId, payload, serverSeq?: number }`.

| type | payload | effect |
|---|---|---|
| `debt.set_initial` | `{prayer, count}` | sets the starting debt for one prayer; one per prayer, latest wins |
| `debt.adjust` | `{prayer, delta, note?}` | adds delta to debt |
| `qada.logged` | `{prayer, count, prayerDay}` | subtracts count |
| `daily.resolved` | `{prayerDay, prayer, status}` | `missed` adds 1; others add 0; latest resolution for the pair wins |
| `strategy.started` | `{strategyId, name, rules, order}` | closes the open period, opens a new one |
| `strategy.stopped` | `{strategyId}` | closes the open period |
| `event.revoked` | `{target: uuid}` | removes the target from all reductions |

**Reducer** `reduce(events): LedgerState` returns per-prayer confirmed debt, resolutions map keyed `prayerDay|prayer`, qada logs by prayer day, strategy periods, and the revoked set. Deterministic: sort by `(occurredAt, id)` before reducing.

**Prayer-day engine** (`prayerDay.ts`): given settings, a location, a timezone and an instant, returns the prayer day, the five or six windows, the current window, and the pending set (windows closed with no resolution). Wraps adhan-js. In "no windows" mode returns the civil date and no windows.

**Strategy engine** (`strategy.ts`): rule types

```ts
type Rule =
  | { kind: 'with_daily'; daily: Prayer; qada: Prayer | 'same' | 'next_in_order'; count: number }
  | { kind: 'block'; label: string; after: Prayer | 'any'; qada: Prayer | 'next_in_order'; count: number }
  | { kind: 'daily_quota'; qada: Prayer | 'next_in_order'; count: number };
```

`targetsFor(day, state, strategy)`, `progressFor(day, state, strategy)` (greedy per Deferred Unknown 1), `adherence(period, state)`, `simulateFinish(state, strategy)` (day-by-day to zero, capped at 100 years), `paceFinish(state, trailingDays = 30)`.

**Tests:** vitest. Property-style tests on the reducer (order independence after sort, revoke idempotence), boundary tests around Fajr and midnight for the prayer-day engine, and simulation tests for each template strategy against known totals (for example 4,000 per prayer with "One with each" finishes in about 4,000 days).

### Client store and sync (`src/store`)

Dexie database `qadaos` with tables `events` (indexed by `id`, `serverSeq`, `synced`), `settings`, `meta`. On boot, load events, reduce, render. Every user action writes an event locally first, updates the derived state, then enqueues.

Sync loop: on boot, on `online`, on visibility change and after every local write, `POST /api/sync/push` with unsynced events in batches of 500; then `GET /api/sync/pull?since=<maxServerSeq>`; merge and re-reduce. Request `navigator.storage.persist()` once after sign-in. Offline banner reads from the unsynced count.

### API (Next.js route handlers, all under `/api`)

All routes require a session except auth callbacks, the reminder dispatch (shared secret header) and the privacy page. All bodies validated with zod. Errors return `{ error: { code, message } }` with stable codes listed in `src/lib/errors.ts`.

| route | method | purpose |
|---|---|---|
| `/api/auth/[...all]` | any | better-auth handler (Google, passkeys, sessions) |
| `/api/sync/push` | POST | insert events, return accepted ids and new `serverSeq` values |
| `/api/sync/pull` | GET | events with `serverSeq > since`, max 2,000 per page |
| `/api/settings` | GET, PUT | settings document, last-write-wins |
| `/api/push/subscribe` | POST, DELETE | register or remove a device subscription |
| `/api/reminders/dispatch` | POST | scheduler-triggered; sends reminders due in the last 5 minutes |
| `/api/account/export` | GET | JSON export, streamed |
| `/api/account` | DELETE | full deletion |

Rate limits per Assumption 17.

### Database (Postgres, Drizzle migrations)

- `users`, `sessions`, `accounts`, `passkeys`, `verifications`: better-auth tables.
- `ledger_events`: `id uuid pk`, `user_id`, `type text`, `occurred_at timestamptz`, `tz text`, `device_id text`, `payload jsonb`, `server_seq bigserial unique`, `received_at timestamptz default now()`. Index `(user_id, server_seq)`.
- `user_settings`: `user_id pk`, `doc jsonb`, `updated_at timestamptz`.
- `push_subscriptions`: `id`, `user_id`, `endpoint text unique`, `p256dh`, `auth`, `created_at`, `last_seen_at`.
- `reminder_dispatches`: `user_id`, `prayer_day date`, `kind text`, `sent_at`, primary key `(user_id, prayer_day, kind)` for idempotence.

Forward-only migrations. Greenfield, so no existing-row defaults to walk in v1.

### Reminders

The dispatch endpoint loads all users with reminders enabled, computes today's prayer times from their stored settings via the domain package, and for each reminder whose time falls in `[now − 5 min, now)` and has no `reminder_dispatches` row, sends a Web Push (web-push library, VAPID) to every subscription and records the row. The daily review nudge is a `kind` like `review` computed from Isha plus the configured offset. Subscriptions returning 404 or 410 are deleted. The whole run must finish under the function timeout; log the run duration.

### PWA shell

Serwist service worker: precache the app shell, network-first for API calls, no caching of sync responses. Manifest with `display: standalone`, theme color the cream ground, maskable icons, iOS splash images. Update toast per Deferred Unknown 6.

### Auth

better-auth with Google provider and passkey plugin. Google redirect URIs registered for local, preview and production hosts. Passkey registration offered on the first home-screen visit after sign-in, via a dismissible card.

## Risks & Gotchas

1. **Phantom debt from forgotten logs.** Mitigated by the pending state, the review nudge and one-tap undo. Never auto-mark missed.
2. **iOS storage eviction or reinstall wipes local data.** Mitigated by server sync as truth plus `storage.persist()`. The client re-pulls everything after sign-in.
3. **Web Push on iOS only works installed.** Mitigated by the install card and by checking `navigator.standalone` before offering reminders on iOS.
4. **Scheduler granularity.** Vercel Hobby cron cannot hit prayer times. QStash per Assumption 2. Dispatch is idempotent so overlapping runs are safe.
5. **Prayer times disagree between client and server.** Same library, same stored parameters, same version pin. Add a test that compares both for a fixed location and date.
6. **Timezone travel** makes a day ambiguous. Events store their tz; Deferred Unknown 2.
7. **Double-tap double logging.** Buttons disable for 300 ms after a tap; every event is undoable.
8. **Sync race on two devices** resolving the same pending prayer differently. Deterministic ordering per Deferred Unknown 5.
9. **Abuse of a public service:** signup spam or event floods. Google-only signup raises the bar; rate limits per Assumption 17; a per-user event cap of 1,000,000 is enforced at push.
10. **Special-category data.** Minimal collection, immediate deletion, plain privacy page. No analytics that carries prayer data; if analytics is added later it counts page views only.
11. **Google OAuth misconfiguration** (missing redirect URI per environment) blocks all login. Documented in README with the exact three URIs.
12. **Large event logs slow the reducer.** 20,000 qada logged one at a time over years is well under 100,000 events; reduce is linear. Deferred Unknown 3 covers the escape hatch.
13. **Fiqh disagreement from users.** Every fiqh-sensitive behavior is a setting with neutral default, and the README states the app takes no position.
14. **Guilt-driven abandonment.** No streaks, no red badges for misses, the missed state is a fact not a warning.

## Non-goals

- Fasting qada, zakat or any other obligation. The event `type` namespace leaves room (`fast.*`) but nothing is built.
- Arabic or any second language.
- Social features, sharing progress, leaderboards.
- Native app wrappers.
- Enforcing make-up order (tartib).
- Traveler (qasr) or combined prayer accounting beyond normal logging.
